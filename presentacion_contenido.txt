DIAPOSITIVA 5 — TECNOLOGÍAS Y ARQUITECTURA
--------------------------------------------------------------
[GRÁFICO]: Diagrama de capas (pirámide o columnas):
           - Capa UI: Jetpack Compose, Navigation
           - Capa ViewModel: MVVM
           - Capa Domain: Clean Architecture (Use Cases)
           - Capa Data: Room, DataStore, Repositories
           - Capa DI: Hilt
           Debajo: Módulos Gradle (core:domain, core:data, feature:auth, etc.)

QUÉ DECIR:
"La arquitectura del proyecto sigue el patrón MVVM con Clean Architecture,
organizado en 8 módulos Gradle independientes.

MVVM significa Model-View-ViewModel: la UI (View) solo muestra datos, el
ViewModel los prepara y expone, y el Model (capas de dominio y datos)
contiene toda la lógica de negocio.

Clean Architecture agrega una separación estricta por capas: la capa de dominio
no sabe nada de Android ni de bases de datos, solo define qué puede hacer el sistema.
Esto hace que sea mucho más fácil de testear y de mantener.

Para la base de datos local usamos Room (una librería de Google que simplifica
SQLite en Android) y para la sesión usamos DataStore (el reemplazo moderno de
SharedPreferences, también de Google).

La inyección de dependencias la maneja Hilt, que permite que cada clase reciba
lo que necesita sin tener que instanciarlo manualmente."

TÉRMINO A EXPLICAR — Inyección de dependencias (DI):
"En lugar de que una clase cree sus propias dependencias (por ejemplo,
que el ViewModel cree su propio repositorio), un contenedor externo (Hilt)
las provee. Esto facilita el testing porque en los tests podemos reemplazar
las dependencias reales por versiones simuladas (mocks)."

--------------------------------------------------------------
DIAPOSITIVA 8 — ¿QUÉ ES LA RTM?
--------------------------------------------------------------
[GRÁFICO]: Definición en recuadro + diagrama lineal:
           REQUERIMIENTO → MÓDULO → CLASE / USE CASE → TEST → CI

QUÉ DECIR:
"RTM significa Requirements Traceability Matrix, o Matriz de Trazabilidad
de Requerimientos. Es un documento que vincula cada requerimiento con
el código que lo implementa y los tests que lo verifican.

¿Para qué sirve? Nos permite demostrar que nada se quedó sin implementar
y que nada se implementó sin un requerimiento que lo justifique. Si alguien
pregunta 'probaron que el login funciona?' podemos señalar exactamente qué
tests lo cubren y en qué línea del código.

Nuestra RTM sigue el estándar IEEE 730 §7 (el estándar internacional para
planes de aseguramiento de calidad de software) y está en su versión 3.0."

TÉRMINO A EXPLICAR — IEEE 730:
"Es un estándar de la IEEE (Instituto de Ingenieros Eléctricos y Electrónicos,
el organismo que define estándares de ingeniería a nivel mundial) que especifica
cómo estructurar un Plan de Aseguramiento de Calidad de Software (SQA Plan).
Define qué documentos hay que producir, qué revisar, y cómo medir la calidad."

--------------------------------------------------------------
DIAPOSITIVA 9 — REQUERIMIENTOS FUNCIONALES
--------------------------------------------------------------
[GRÁFICO]: Tabla con los 7 requerimientos funcionales + 2 no funcionales,
           con columna de estado (todos en verde ✅ excepto REQ-NF02 en amarillo ⚠️).

QUÉ DECIR:
"El sistema tiene 7 requerimientos funcionales, que son las funciones que
el sistema DEBE hacer, y 2 requerimientos no funcionales, que describen
CÓMO debe hacerlas (calidad de servicio).

- REQ-F01: Autenticación — registro, login, selección de rol (Comercio o Consumidor)
  y gestión de sesión persistente.
- REQ-F02: El comercio publica packs con descuento. Validamos que el precio
  con descuento sea efectivamente menor al original.
- REQ-F03: El consumidor ve packs disponibles en un radio configurable.
- REQ-F04: El consumidor reserva un pack. Esta operación es ATÓMICA para
  evitar que dos usuarios reserven el mismo pack simultáneamente.
- REQ-F05: El comercio marca una reserva como retirada.
- REQ-F06: El consumidor cancela una reserva activa.
- REQ-F07: El consumidor puede marcar packs como favoritos y ver su lista.

Los requerimientos no funcionales son:
- REQ-NF01: Exclusividad de reservas bajo concurrencia — esto es clave y lo
  veremos en detalle en la sección de pruebas.
- REQ-NF02: El APK no supera 50 MB — está parcialmente verificado
  (requiere build de release manual).

Todos los funcionales están en estado ✅ Implementado."

TÉRMINO A EXPLICAR — Operación atómica:
"Una operación atómica es aquella que se ejecuta completamente o no se ejecuta
en absoluto: nunca queda en un estado intermedio. En nuestro caso, cuando
dos usuarios intentan reservar el mismo pack al mismo tiempo, el sistema
garantiza que solo uno tiene éxito. Esto lo implementamos con una transacción
@Transaction de Room que hace un UPDATE condicional en la base de datos."

DIAPOSITIVA 14 — MÉTRICAS DE CALIDAD: ANÁLISIS ESTÁTICO
--------------------------------------------------------------
[GRÁFICO]: Tabla con 3 métricas y sus valores:

           ┌──────────────────────────────────────────┐
           │ MÉTRICA         │ UMBRAL  │ RESULTADO     │
           │─────────────────┼─────────┼───────────────│
           │ Comp. Ciclomática│ ≤ 10   │ ✅ Cumple     │
           │ (Detekt)         │        │               │
           │─────────────────┼─────────┼───────────────│
           │ maxIssues Detekt │ = 0    │ ✅ 0 warnings  │
           │─────────────────┼─────────┼───────────────│
           │ MI (Mant. Index) │ > 50   │ ✅ Calculado  │
           └──────────────────────────────────────────┘

QUÉ DECIR:
"Para el análisis estático de código usamos Detekt, que es la herramienta
de análisis estático estándar para Kotlin. Corre en cada build del CI.

Complejidad Ciclomática (CC): mide cuántos caminos distintos puede seguir
el código dentro de una función. Una función con muchos if/else/when anidados
tiene alta complejidad ciclomática, lo que la hace difícil de entender y testear.
Fijamos un límite de 10: si una función supera ese valor, el build falla.
Esto nos obligó a refactorizar funciones que estaban creciendo demasiado.

Maintainability Index (MI): es un índice compuesto que combina la complejidad
ciclomática, el volumen del código (cantidad de operadores y operandos) y
las líneas de código. Varía de 0 a 100. Valores sobre 50 indican código
mantenible. Es útil para comparar módulos: un MI bajo en un módulo indica
que merece una refactorización."

TÉRMINO A EXPLICAR — Análisis estático:
"El análisis estático examina el código SIN ejecutarlo. Detecta problemas
potenciales, violaciones de estilo y métricas de calidad solo leyendo el
texto del código fuente. Es complementario a los tests, que sí ejecutan el código."

DIAPOSITIVA 15 — COBERTURA DE CÓDIGO: JACOCO
--------------------------------------------------------------
[GRÁFICO]: Dos barras de progreso grandes y verdes:

           INSTRUCCIONES: ████████████████░░ 84.73%  (umbral: 70%)
           RAMAS:         ████████████████░░ 80.41%  (umbral: 60%)

           Debajo: tabla por módulo con su cobertura individual.

QUÉ DECIR:
"La cobertura de código la medimos con JaCoCo, que es el estándar de
cobertura para proyectos Java y Kotlin.

Tenemos dos métricas:

COBERTURA DE INSTRUCCIONES (84.73%): de cada 100 líneas de código que
se pueden ejecutar, nuestros tests ejecutan 84. Superamos el umbral
del 70% que exige IEEE 730.

COBERTURA DE RAMAS (80.41%): de cada 100 decisiones en el código
(cada if, when, try/catch), nuestros tests recorren 80 caminos distintos.
Superamos el umbral del 60%.

Un 100% de cobertura no garantiza ausencia de bugs, pero una cobertura
baja casi garantiza que hay código que nunca fue probado.

Importante: excluimos deliberadamente los Composables de UI de la cobertura,
porque requieren tests de interfaz de usuario (tests instrumentados) que
están fuera del alcance del proyecto."

TÉRMINO A EXPLICAR — Cobertura de ramas:
"Imagine un if (x > 0): tiene dos ramas, la del 'sí' (x es positivo) y
la del 'no' (x no es positivo). La cobertura de instrucciones solo cuenta
que ejecutamos esa línea; la cobertura de ramas exige que probemos ambos
caminos. Es una métrica más exigente y más valiosa."

DIAPOSITIVA 17 — ESTRATEGIA DE PRUEBAS
--------------------------------------------------------------
[GRÁFICO]: Pirámide de tests:
           - Tope (pequeño): Tests de UI — No implementados (excluidos)
           - Medio: Tests de integración liviana (use case ↔ repositorio)
           - Base (ancho): Tests unitarios (121 tests) — JUnit 4 + MockK

           A los costados:
           - Izquierda: "Caja Negra (Black Box)"
           - Derecha: "Caja Blanca (White Box)"

QUÉ DECIR:
"Nuestra estrategia de pruebas sigue el modelo de pirámide de tests:
muchos tests unitarios en la base (son rápidos y baratos) y menos
tests de integración y UI en la cima.

La base son nuestros 121 tests unitarios, que prueban cada componente
en aislamiento usando MockK para simular las dependencias.

En el medio tenemos tests de integración liviana, donde verificamos que
un caso de uso y su repositorio colaboran correctamente.

Y también tenemos tests de concurrencia, que van más allá de los unitarios:
simulamos múltiples coroutines (hilos de ejecución livianos) compitiendo
por el mismo recurso.

Usamos dos técnicas de diseño: Caja Negra y Caja Blanca."

TÉRMINO A EXPLICAR — MockK:
"MockK es una librería para Kotlin que permite crear objetos 'mock', es decir,
versiones falsas pero controladas de las dependencias. Por ejemplo, en lugar
de conectar con una base de datos real, el test usa un mock del repositorio
que devuelve datos predefinidos. Esto hace los tests rápidos, predecibles
y ejecutables sin un dispositivo Android real."

TÉRMINO A EXPLICAR — Coroutines:
"Las coroutines son la forma de Kotlin de ejecutar código asíncrono: operaciones
que pueden tomar tiempo (como consultar una base de datos o una red) sin bloquear
el hilo principal de la app. Son más eficientes que los threads tradicionales
porque miles de coroutines pueden ejecutarse en pocos threads reales."

DIAPOSITIVA 18 — CAJA NEGRA vs CAJA BLANCA
--------------------------------------------------------------
[GRÁFICO]: Dos columnas lado a lado:

           CAJA NEGRA                    CAJA BLANCA
           ──────────                    ────────────
           El tester NO conoce el        El tester SÍ conoce el
           código interno.               código interno.

           Solo importan:                Se verifican:
           Entrada → Resultado           Ramas, condiciones,
                                         llamadas a colaboradores

           Ejemplo TC-01:                Ejemplo TC-09:
           email + password →            La rama 'contraseña incorrecta'
           ¿devuelve Success?            → ¿retorna el error correcto?

QUÉ DECIR:
"Caja Negra: probamos el sistema desde afuera, como un usuario. Solo nos
importa qué entra y qué sale. No nos importa cómo el código internamente
llega al resultado. Es la perspectiva del usuario.

Caja Blanca: conocemos el código y diseñamos tests para recorrer caminos
específicos. Queremos asegurarnos de que cada rama condicional se pruebe.
Es la perspectiva del desarrollador.

Documentamos 8 casos de caja negra y 8 de caja blanca, para un total de
16 casos de prueba. En la siguiente diapositiva vemos ejemplos concretos."

DIAPOSITIVA 21 — REPORTE DE DEFECTOS
--------------------------------------------------------------
[GRÁFICO]: Tabla de defectos:

           ID     | Severidad | Estado
           DEF-001 | Alta      | Abierto
           DEF-002 | Media     | Abierto
           DEF-003 | Alta      | ✅ RESUELTO
           DEF-004 | Media     | Abierto
           DEF-005 | Baja      | Abierto
           DEF-006 | Media     | Abierto

           Gráfico de torta: 1 Alta abierto / 1 Alta resuelto / 3 Media / 1 Baja

QUÉ DECIR:
"Durante el desarrollo identificamos y documentamos 6 defectos formales.
Para cada uno especificamos: severidad, módulo afectado, pasos para reproducir,
impacto en el sistema y corrección sugerida.

DEF-001 (Alta, Abierto): Uso de hashCode() de Java para almacenar contraseñas.
hashCode() NO es una función criptográfica; es reversible, no usa sal (salt)
y varía entre versiones de JVM. En un sistema productivo habría que usar
BCrypt o PBKDF2. Lo dejamos documentado como deuda técnica crítica.

DEF-002 (Media): La búsqueda de packs no filtra por distancia real. Está
documentado en el código como 'comportamiento MVP', pero es una brecha con
REQ-F03. La corrección sería implementar la fórmula de Haversine.

DEF-003 (Alta, RESUELTO): El más grave que resolvimos. El método getCurrentUser()
siempre devolvía null. Esto hacía que ViewModels usaran IDs hardcodeados y
la sesión no persistía entre reinicios de la app. La solución fue implementar
SessionManager usando Jetpack DataStore. Agregamos 9 tests de regresión para
verificar la corrección."

TÉRMINO A EXPLICAR — Deuda técnica:
"La deuda técnica son decisiones de implementación que sabemos que no son
las óptimas pero que aceptamos conscientemente por restricciones de tiempo
o alcance. Como una deuda financiera, con el tiempo 'paga intereses': el
código se vuelve más difícil de mantener. Lo importante es documentarla
para que el equipo sepa que existe."

TÉRMINO A EXPLICAR — Salt / Sal criptográfica:
"Una sal es un valor aleatorio que se agrega a la contraseña ANTES de aplicar
el hash. Esto garantiza que dos usuarios con la misma contraseña tengan hashes
distintos, y hace que los ataques de tabla arcoíris (listas precomputadas de
hashes) sean ineficaces."

TÉRMINO A EXPLICAR — Fórmula de Haversine:
"Es la fórmula matemática para calcular la distancia entre dos puntos en la
superficie de una esfera (como la Tierra) usando sus coordenadas de latitud
y longitud. La usaríamos para filtrar los packs que estén dentro del radio
configurado por el usuario."

DIAPOSITIVA 22 — ¿POR QUÉ IMPORTA EL UX?
--------------------------------------------------------------
[GRÁFICO]: Cita famosa de Nielsen: "If users can't use a feature, it doesn't work."
           O simplemente: "Un software que nadie sabe usar, no funciona."

QUÉ DECIR:
"Un sistema puede ser técnicamente impecable, con arquitectura perfecta,
tests al 100% y cero defectos, y aun así fracasar si los usuarios no lo
entienden o no lo disfrutan usar.

La experiencia de usuario (UX) es la disciplina que se ocupa de que el
sistema sea intuitivo, eficiente y satisfactorio para las personas que
lo usan. No es solo hacer que sea bonito: es asegurarse de que cumple
su propósito desde la perspectiva del usuario.

Para evaluar nuestras pantallas usamos las 10 heurísticas de usabilidad
de Jakob Nielsen, que son los principios de diseño más ampliamente
adoptados en la industria."

--------------------------------------------------------------
[GRÁFICO]: Lista de las 10 heurísticas con íconos:

           2. Coincidencia sistema/mundo real
           3. Control y libertad del usuario

QUÉ DECIR:

siguen siendo el estándar para evaluar la usabilidad de cualquier interfaz.

investigación empírica sobre cómo los usuarios perciben e interactúan

"Reflexionando sobre el proceso, identificamos cuatro aprendizajes clave:

1. ARQUITECTURA COMO INVERSIÓN: Al principio, configurar 8 módulos Gradle

   ausente de los documentos. Sin trazabilidad, eso habría quedado como
   un agujero en la defensa.

4. LOS DEFECTOS COMO APRENDIZAJE: DEF-001 nos hizo investigar BCrypt y

GLOSARIO RÁPIDO DE TÉRMINOS A TENER A MANO:

- Kotlin: Lenguaje de programación moderno para Android, creado por JetBrains,
  oficial de Google desde 2017. Es más conciso y seguro que Java.

- Gradle: Sistema de construcción (build system) de proyectos Android.
  El "multi-módulo Gradle" significa que el proyecto está dividido en
  subproyectos independientes que se compilan por separado.

- Room: Librería de Google que simplifica el uso de SQLite (base de datos
  relacional) en Android. Genera código automáticamente a partir de anotaciones.

- DataStore: Librería de Google para almacenar datos clave-valor en Android.
  Reemplaza a SharedPreferences con mejor soporte para operaciones asíncronas.

- Hilt: Framework de inyección de dependencias para Android, basado en Dagger.

- Flow: Un tipo de dato en Kotlin que representa una secuencia de valores
  emitidos de forma asíncrona. Similar a un Observable de RxJava.
  Lo usamos para observar cambios en la base de datos en tiempo real.

- @Transaction en Room: Garantiza que un conjunto de operaciones de base de
  datos se ejecutan de forma atómica. Si alguna falla, todas se revierten.

- UseCase (Caso de Uso): En Clean Architecture, una clase que encapsula una
  única acción de negocio. Por ejemplo, LoginUserUseCase solo sabe cómo
  hacer login; no sabe nada de UI ni de base de datos.

- ViewModel: Componente de la arquitectura MVVM que sobrevive rotaciones de
  pantalla y expone datos a la UI a través de StateFlow.

- StateFlow: Un tipo especial de Flow que siempre tiene un valor actual y
  notifica a los observadores cuando cambia. Los ViewModels lo usan para
  informar a la UI sobre el estado actual.

TIPS PARA LA PRESENTACIÓN:
- La demo en vivo es el momento más arriesgado. Tener capturas de pantalla
  como respaldo en una diapositiva de "backup".
- Para el TC-16 (concurrencia), considerar mostrar el código del test
  y el output del CI en lugar de intentar ejecutarlo en vivo.
- Si preguntan sobre el hash inseguro (DEF-001): explicar que es deuda
  técnica conocida y documentada, y que en producción usaríamos BCrypt.
- Si preguntan sobre la cobertura del 84%: aclarar que el 16% restante
  son principalmente Composables de UI que requieren tests instrumentados
  (que corren en un dispositivo real o emulador, no en JVM local).
